PROJECT LEAD

Mission & organisation

Set the course: what we protect, against whom, and who does what.

▶ Briefing: slides 1–9 and 25–26

Key points

DICThree goals

Keep the archive available, intact and confidential (the CIA triad).

0Zero trust

The Greys are already inside. Nobody is trusted by default, not even colleagues.

5Five agents, four services

Infra, security, dev and project lead. Each one owns a part of the plan.

The diagram

  1. Think of Zone 67 as a fortress. Everything from outside hits one guard post: the firewall. By default, it says no.
  2. Inside, five separate buildings with badge doors. In IT, each building is called a VLAN.
  3. The archive of Recorder 451 lives alone in its own vault: VLAN 50.
  4. An infected PC in the users' zone tries to reach the vault. The firewall blocks it.
  5. Admins working from home use a private tunnel (VPN) and a phone code, and may only enter by the escorted door: the bastion.
  6. Backups leave the site: an off-site copy pulls them, and a tape with no cable keeps one more.

In plain words

Zone 67 is a fortress. One guard post at the gate (the firewall), five separate buildings inside (the VLANs), and a vault for the archive.

Say it at the oral

“Our mission: keep Recorder 451’s archive available, intact and out of the Greys’ reach.”

INFRA

Server, network & recovery

Build the foundation (one solid server, a network split into zones) and know how to restart everything after a disaster.

▶ Briefing: slides 10–13, then 26–27Source: NIST [4]

Key points

7One server, seven VMs

One virtual machine per role. If one breaks, the others keep running.

5Five network zones

An infected PC stays stuck in its zone. The archive has its own.

×2Everything doubled

Two disks, two power supplies, two links, two domain controllers.

4 hRecovery targets

For the archive: never more than 4 h of lost work, never more than 4 h of downtime.

The diagram

  1. At the bottom, one real machine. Almost everything is doubled: disks, cables, power.
  2. A software called Proxmox splits it into several virtual machines, like one building split into rooms.
  3. One room per job: accounts, files, alarms… If one breaks, the others keep running.
  4. The archive of Recorder 451 gets its own locked room: its own zone and an encrypted disk.
  5. A disk dies? Its twin keeps going. The accounts server stops? Its copy takes over.
  1. 09:00: the last good backup. Everything before this point is safe.
  2. 11:30: ransomware hits the archive.
  3. The work done since 09:00 is lost. That gap is the RPO: how much we accept to lose.
  4. Back online at 13:30. The time without service is the RTO: how long we accept to wait.
  5. Our target for the archive: never more than 4 hours of either. Here, we are within it.

In plain words

The server is a building split into rooms (the VMs). Proxmox is the caretaker: it gives each room its walls, water and power.

Say it at the oral

“One VM per role and nothing extra on it: the less software, the fewer doors for the Greys.”

Flow matrix: who may talk to whom
  • From the Internet, one port only: OpenVPN 1194/udp on the firewall.
  • Users reach the archive only over HTTPS, with the “archive” role and MFA.
  • The archive never talks to the Internet.
  • Admin traffic (SSH, RDP) only leaves the administration zone, through the bastion.
  • Everything else is blocked and logged.
Installation in ten steps
  1. Rack and cable two power supplies, two 10 Gb/s links.
  2. Lock the firmware BIOS password, Secure Boot, TPM.
  3. Build the RAID RAID 1 system, encrypted RAID 10 data.
  4. Install Proxmox fixed IP in VLAN 10, admin with MFA.
  5. Set up the network LACP, VLAN-aware bridge, one tag per VM.
  6. Create the VMs from hardened templates, deployed with Ansible.
  7. Deploy Active Directory domain zone67.lan, DNS, DHCP, then DC02.
  8. Deploy the services archive, shares, intranet, SIEM, bastion.
  9. Raise the Shield ANSSI / CIS hardening (Security file).
  10. Start Godkiller schedule backups, first full restore test (Dev file).

SENTINELCyber expert
SECURITY

Remote access & the Shield

Keep the Greys out, and see them if they try.

▶ Briefing: slides 14–17Source: ANSSI [3]

Key points

4Four checkpoints

VPN, firewall, bastion, then the server. No admin ever connects directly.

6Six layers of defence

If one layer gives way, the next one stops the attacker.

AESEncrypted everywhere

On the disks and on the network. No protocol in clear text.

24/7Everything watched

The SIEM collects every log and raises the alarm.

The diagram

  1. An admin at home needs to fix a server inside Zone 67. No direct access is allowed.
  2. Checkpoint 1: a private, encrypted tunnel (VPN). To open it: a digital ID card and a code on the phone.
  3. Checkpoint 2: the guard post (firewall) lets the tunnel reach only one door.
  4. Checkpoint 3: that door, the bastion, is an escorted entrance. It asks for a second code and films everything.
  5. Checkpoint 4: only then does the bastion open the server. Every action is traced.
  1. Like the walls of a fortress, one after the other. Outside: a locked room with badge and camera, then the guard post.
  2. Inside: separate buildings, and machines with only what they need, always up to date.
  3. At the centre: personal accounts with a password and a phone code, and an archive that is encrypted.
  4. An attacker who breaks one wall meets the next, and every wall sounds the alarm in our control room (the SIEM).

In plain words

The bastion is the guard post: you sign the register, you are escorted, and the camera is rolling. The SIEM is the CCTV room.

Say it at the oral

“An admin never connects straight to a server. He goes through four checkpoints, and every session is recorded.”

Words to know

VPN
An encrypted tunnel through the Internet.
MFA
A password plus a second proof, like a code on your phone.
Bastion
The only, recorded entrance for admins.
SIEM
Collects all logs and raises security alerts.
RBAC
Rights are given to roles, and people get a role.

Technical sheet — going further

Strong authentication & roles
  • Named accounts only, no shared “admin” account.
  • MFA on the VPN, the bastion, Proxmox and the archive.
  • Roles: archive reader, archive admin, backup operator, auditor.
  • Two-person rule: no single account can delete the archive.
  • LAPS: a different local admin password on every machine.
Encryption
  • At rest: LUKS on ARCH01, BitLocker on Windows VMs, encrypted backups.
  • In transit: TLS 1.3, SSH, OpenVPN, IPsec.
  • No Telnet, FTP or HTTP.
  • Keys are never stored next to the data they protect.
Firewall & lockdown
  • Default deny on every VLAN.
  • SSH and RDP only from the bastion; SSH by key, no root login.
  • fail2ban and account lockout after failed attempts.
  • USB sticks blocked by GPO.
Detection & patching
  • Wazuh agent on every VM, logs kept for one year.
  • Suricata IDS on the firewall.
  • Alerts: new admin, archive opened at night, mass deletion, failed backup.
  • Monthly patching window and monthly vulnerability scan (OpenVAS).

Secure app & Godkiller

Code the tools of Zone 67 and secure them from the inside: the archive app and the Godkiller backup software.

▶ Briefing: CYPHER 18–20 · RELAY 21–25Source: OWASP [5]Source: Veeam [2]Source: CISA [1]

Key points

OWASPSecure in the code

CYPHER: log-in, role check on every request, no SQL injection, encrypted data, every read logged.

3-2-1-1-0Godkiller, the software

RELAY codes the scripts that apply the rule: 3 copies, 2 media, 1 off-site, 1 untouchable, 0 errors.

AUTOProof it works

A dashboard in green or red, instant alerts, and a restore test run by a script every month.

The diagram

  1. An archivist wants to read a document. Everything goes through the archive app, coded by CYPHER.
  2. Gate 1, log-in: the password is never stored as is (it is hashed), and a code on the phone is required.
  3. Gate 2, the role: on every click, the code checks that this role may see this document.
  4. Gate 3, the prepared query: an attacker types SQL code into the search box. It is treated as plain text, so the injection fails.
  5. Documents are encrypted in the database, and every read goes into the log, sent to SENTINEL’s SIEM.
  1. Every night, the server sends an encrypted copy to backup vault #1, in another room.
  2. The key lives on paper, in a different safe. A stolen backup is useless without it.
  3. Vault #2, on another ministry site, comes to fetch the copies itself. Nobody in Zone 67 can log into it.
  4. Every Sunday, a tape that can be written only once: nobody can erase it. It rests in a safe, with no cable.
  5. Deleting a backup needs two people. And every month we test a restore.

In plain words

SENTINEL guards the ramparts; CYPHER reinforces the doors from inside the app. RELAY is the conductor of the backups: she does not copy anything by hand, she coded the one who does.

Say it at the oral

“SENTINEL protects around the app; we protect it from the inside, in the code.”

From code to production
  1. Write the code on a separate branch, never directly in production.
  2. Review a second dev reads every change (two-person rule, applied to code).
  3. Test automatic tests and a security scan (SAST) run on every change.
  4. Release only if everything is green; secrets come from a vault, never from the code.
Godkiller in code
  • Scripts: Python scripts drive the Proxmox Backup Server API (start jobs, check results).
  • Dashboard: a small web page shows every job in green or red.
  • Alerts: a failed or missing backup sends an e-mail and a Wazuh alert within minutes.
  • Restore test: every month, a script restores a VM in an isolated bubble and compares file fingerprints.

Godkiller safeguards
  • Separate keys: AES-256 encryption, key on paper in another safe kept by COMMAND.
  • Pull, not push: server #2 fetches the data; nobody in Zone 67 has an account on it.
  • WORM tape: once written, nobody can modify or erase it, not even an admin.
  • Two-person rule: deleting backups needs COMMAND + SENTINEL.
  • Retention: server #1 7 daily, 4 weekly, 6 monthly · server #2 12 monthly · tape 12 monthly + 5 yearly.
